## Why a placeholder is the honest design

1. **A program id is a commitment, not a label.** Once a Solana program
   is deployed, its id is immutable for the life of the deployment.
   Burning the final keypair into a repository before the buyer takes
   custody would mean the buyer either deploys under the SELLER's key
   (unacceptable) or upgrades under a key they do not control
   (unacceptable).
2. **PDAs must be derivable before deployment.** Tests, vault/treasury
   address derivations, and integration fixtures need a stable id
   during development; a documented placeholder with a guarded swap
   path is the only way to have both.
3. **Nothing is hidden.** The placeholder status is printed by the
   verification script itself, every time, in plain text. A buyer
   cannot accidentally believe the id is live.

## The guarded path from placeholder to final identity

`scripts/staking-identity.sh` provides three subcommands:

* **`verify`** — all references agree, and the placeholder status is
  displayed. Run it at any time; it never mutates anything.
* **`set-id <program-keypair.json>`** — when the FINAL program keypair
  exists (generated by the deploying operator/buyer, never by this
  repository), the `declare_id!` value and every buyer-facing document
  are updated atomically and re-verified. Historical records
  (`AUDIT.md`) and the delivery-time release record
  (`release-manifest.json`) are deliberately NOT rewritten — they
  document the past.
* **`deploy`** — deploys `target/deploy/staking_suite.so` ONLY when:
  1. the supplied program keypair's public key equals the declared id,
  2. the binary is up to date with the source (rebuild check), and
  3. for any non-localhost cluster, the declared id is no longer the
     placeholder.

  On any mismatch the deploy refuses. Nothing in the script can invent
  an identity: `set-id` requires a real keypair file the operator
  generated and controls.

## Authority status

The upgrade authority for the deployed program will be whoever holds
the FINAL program keypair — which this repository does not and never
did hold. The placeholder id's keypair is not in the tree (verified by
the release contamination scan: no keypairs or secrets ship). After
purchase the buyer generates the final keypair OUTSIDE this
repository, runs `set-id`, and becomes the sole upgrade authority;
`deploy` enforces that the keypair matches the declared id, so no one
else's key can be burned in. Authority rotation after deployment is a
Solana `set_upgrade_authority` operation outside this repository's
scope and is documented as such.

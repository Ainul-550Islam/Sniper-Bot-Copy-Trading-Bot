### HA feed cursors are fenced, monotonic and replay-safe (2026-11-09)
Feed progress used to be a blind upsert: any process, any lease generation, any time could overwrite another worker's cursor, and the advance was written **before** the caller processed the event — so a crash in between skipped that event forever. Now (migration 0080) `ha_cursors` carries `pending` and `fence`, and one admission matrix (`FeedCursor::admit_write`, implemented identically in PostgreSQL as a single `verdict` CTE) decides every write: an older generation, a different holder at the same generation (split brain) and an unfenced writer against a fenced row are refused as `Fenced`; a backwards or repeated write over an unacknowledged advance is refused as `Stale`. The caller gets `CursorAdvance::Refused` and must not process — believing an advance that did not land was the failure being fixed. Advances are `pending` until `HaRuntime::acknowledge` confirms the side effect; an unacknowledged advance is **re-delivered** after a crash or takeover instead of being skipped (at-least-once; the feed journals remain the money-level dedupe). Shutdown and `replay_from` write fenced rather than blind. RED→GREEN: re-injecting the blind upsert and the acknowledged-on-write advance fails 4 unit tests plus the real-Postgres witness (`evidence/claim-gate/ha-cursor-fencing-red-2026-11-09.txt`) and passes with the fix (`ha-cursor-fencing-after-2026-11-09.txt`: core HA 41/41, distributed 18/18, `ha_cursor_fencing_pg` 1/1, modules 79 + 185, Clippy/fmt/diff clean).

Scope: at-least-once delivery means a consumer must still dedupe (the fill/event journals do). The cursor lease and the cursor row are separate: a worker with no lease writes an **unfenced** row, which can never displace a fenced one but is not itself protected from another unfenced process — that remains a single-process-mode assumption, unchanged by this work. `ha_cursors` rows are never pruned; a feed that stops being consumed keeps its last position indefinitely (visible, not harmful).

Now: raw amounts are `volume`/`fees` with `volume_unit`/`fees_unit = raw_trade_amount_unlabelled`; the latency is `avg_execution_latency_ms` with a unit note that it is not fill time; `reverted_txs` is `null` with a reason (an attempt is not a transaction) and the attempt count keeps its own name; and the response carries a `units` block naming which fields are genuinely USD (only the global-ledger-fed `tenant_daily_accounting` figures), which are unlabelled, and why each unavailable metric is unavailable. `GET /api/tenant/integrations` no longer labels a healthy health-registry sample `live_verified` — it says `sampled` plus an `evidence_level_meaning` that spells out that live verification is never claimed from health alone. RED→GREEN: restoring the old labels fails `analytics_vocabulary_never_relabels_raw_amounts_or_latency` and `a_healthy_sample_is_never_labelled_live_verified` (`evidence/platform-fee-review/analytics-units-before-2026-11-09.txt`, both runs recorded) and passes with the fix (`analytics-units-after-2026-11-09.txt`: server api 40/40, trading data plane 56/56, OpenAPI 7/7, router 3/3, Clippy/fmt/diff clean).

Scope: this is a labelling/honesty fix, not new analytics. `win_rate_pct`, `sharpe_ratio` and `avg_slippage_bps` remain `null` with stated reasons; the USD figures still come from `tenant_daily_accounting` and inherit whatever that table's producers record; nothing here proves a venue fill or a chain settlement.

### Same-ID accounting payload mismatch is named, not swallowed (2026-11-09)
The journal's "already booked" answer used to be trusted without comparing payloads, so a durable row written under the same event id with different economics could be treated as a harmless duplicate. Now the durable conflict path records the contested local event, compares it field by field with every durable row under that id and refuses with a reason that names what diverged (`diverging fields: quantity, fee`), latches the conflict and fires the cluster halt exactly as before. The operator surface `GET /api/accounting/conflict` also returns `payload_mismatches`: for each contested id the local event, every durable row, and the diverging field names — read-only, with the latch and the fail-closed state untouched. Hydration of a durable row under an already-applied id logs the same field-level divergence instead of only latching. RED→GREEN: treating every "already booked" as a duplicate fails four ledger tests including `a_durable_row_with_different_economics_names_the_diverging_fields` (`evidence/platform-fee-review/same-id-payload-before-2026-11-09.txt`); with the comparison the core accounting suite is 58/58, the server api 38/38, OpenAPI 7/7 and router conformance 3/3 (`same-id-payload-after-2026-11-09.txt`).

Scope: this **detects and describes** a same-id divergence; it does not decide which side is right — the repair path (journal rebuild) remains the only resolution, and it still needs a human. Timestamps and free-text detail are deliberately excluded from the comparison, so a row that differs only there is still a duplicate.

### Proven ledger conflict escalates to the deployment kill switch (2026-11-09)
The journal-conflict fence was process-local: replica B, which had not observed the divergence, kept booking and kept accepting entries off a book that replica A had already proven untrustworthy. Now the detection itself escalates — `GlobalLedger::attach_conflict_halt` registers a `ConflictHalt` hook that fires **exactly once per process, on the transition into a proven conflict** (never per rejected event, never for a plain validation rejection), and the server's implementation (`ClusterConflictHalt` in `crates/server/src/accounting.rs`) engages the deployment-wide kill switch (`AppState::publish_accounting_conflict`), which every replica applies immediately because kill-ON is the safe flag direction. It is metered (`bot_accounting_conflict_cluster_halts_total{outcome}`) and audits `accounting.conflict.cluster_halt`. Evidence: `evidence/platform-fee-review/cluster-conflict-halt-after-2026-11-09.txt` — core ledger 22/22 (incl. exactly-once and ordinary-rejection-no-halt), global risk 9/9 (halt hook fires before the entry fence is consulted), core state 37/37, server API 36/36, Clippy `-D warnings`/fmt/diff clean.

Scope: this converts a process-local fence into a cluster halt — it does **not** make the divergent book correct, does not repair other replicas automatically (the repair stays the deterministic journal rebuild, `POST /api/accounting/conflict/repair`), and does not stop a trade already in flight. Releasing is deliberately manual: repair, then release the kill switch. The flag channel needs an attached runtime-flags writer (Postgres/Redis) to leave the process — with no durable flag store the halt is local only, exactly like every other cluster flag. **Phase 1.1 remains OPEN.**

### Alternate-signature / duplicate detection for an ambiguous claim (2026-11-09)
A Solana transaction that is re-signed, sent with a different fee payer, or retried after a blockhash refresh lands under a **different** signature than the one the claim recorded — so asking only about the recorded signature can report `absent` for an attempt that is on chain. `reservation_chain::verify_signatures` (and `GET /api/accounting/reservations/signature-scan?trade_key=&signature=&alternates=a,b`) now asks about the recorded signature plus every alternate the operator supplies, and refuses to conclude anything unless all of them agree: **two or more landings ⇒ `duplicate_detected`**, which frees nothing, books nothing, and states that a duplicate send already happened; a single deep landing may be linked (and booked only when `settled_allowed`); a landing under an **alternate** only is reported as landed but `link_allowed=false` — linking an alternate is a human decision; one unlookupable alternate makes the whole scan `unknown`; `abandon` stays forbidden while ANY supplied signature landed; and no chain reader still yields `unknown`, never `absent`. RED→GREEN: hard-wiring `duplicate_detected = false` (and reading a single landing as absence) fails `one_landed_signature_is_linkable_and_never_abandonable` and `two_landed_signatures_are_reported_as_a_duplicate_and_nothing_is_settleable` (`evidence/platform-fee-review/signature-scan-before-2026-11-09.txt`); with the real scan the chain suite is 15/15, chain units 6/6, server api 38/38, OpenAPI artifacts 7/7, router conformance 3/3, Clippy `-D warnings`/fmt/diff clean (`signature-scan-after-2026-11-09.txt`).

Scope: the alternates are whatever a human supplies — nothing derives them automatically, and an alternate the operator never thought of is still invisible. Each signature is read from ONE RPC node at `confirmed`; depth is the slot-distance heuristic above (not a finality proof). A duplicate is **detected and frozen**, not resolved: no reversal, no refund, no ledger action. The new route is documented in `openapi/openapi.{json,yaml}` and covered by router conformance, but no web UI calls it. **Phase 1.1 remains OPEN.**

### Chain-side existence check for an ambiguous claim (2026-11-09)
Freeing a lapsed reservation (`abandon`) lets a retry send, so the operator now gets an answer to the only question that makes that safe: *did the earlier attempt land?* `GET /api/accounting/reservations/chain-check?trade_key=&signature=` (`crates/server/src/reservation_chain.rs`, Readonly role) returns `landed` (the RPC node returned the transaction, with slot, block time, execution error and the signer's post-fee lamport delta), `absent` (the node does not know the signature) or `unknown` (the lookup failed), plus `abandon_allowed` / `link_allowed` and a reason string. The rules are deliberately asymmetric: a **landed** transaction is never abandonable — it must be linked, because freeing the key would let a retry send a second trade; **absent** is not proof of a non-send (an unlanded or evicted transaction looks identical), so `abandon` requires the operator's explicit `operator_asserts_never_sent`; **unknown** authorizes nothing, so an RPC failure can never be read as absence. `POST …/sweep` now enforces this: an `abandon` without that assertion, or of a transaction that is on chain, is refused with 409 and audited, and with no RPC configured the decision is refused rather than made blind. Evidence: `evidence/platform-fee-review/reservation-chain-check-after-2026-11-09.txt` — unit decision matrix 5/5, mock-JSON-RPC probe 4/4 (`landed`/`absent`/`unknown`/malformed signature), server API 36/36, recon 3/3, OpenAPI artifact 7/7, Clippy/fmt/diff clean; the probe is documented at `operator.reservationChainCheck`.

Scope: this reads ONE signature from ONE RPC node at `confirmed` commitment. **Update 2026-11-09 — depth is now reported:** every landed answer carries the node's head slot, the slot distance, a `ChainFinality` of `deeply_confirmed` (≥ `FINALITY_MIN_DEPTH` = 512 slots) or `unfinalized`, and `settled_allowed`, which is true only for a deep landing. A shallow landing, a node that cannot report its slot, and a node whose head is BELOW the transaction slot all report `unfinalized`, so no economics may be booked from them — while `link` stays allowed and `abandon` stays forbidden for every landing, at any depth. Evidence: `evidence/platform-fee-review/chain-finality-before-2026-11-09.txt` (RED: any landing treated as settled ⇒ 3 failures, `left: DeeplyConfirmed, right: Unfinalized`) → `chain-finality-after-2026-11-09.txt` (chain check 9/9, chain unit 6/6, recon 7/7, OpenAPI router 3/3, server api 36/36, Clippy `-D warnings`/fmt/diff clean). This is still **not** a finality proof: it is a slot-distance heuristic read from one node, it does not fetch the block or a root, it does not detect a fork that the queried node itself follows, and it does not detect a transaction that landed at a different signature than the one recorded (the claim stores one signature). It also does not reconcile the resulting fill in the ledger. Live-chain evidence against a real funded provider remains OPEN, and **Phase 1.1 remains OPEN.**

### Confirmed direct-fee ledger posting — narrow scope (2026-11-09)
Copy's direct PumpFun-curve BUY/SELL now posts a `Fee` event to the global accounting ledger **only** when the execution result is live `Confirmed`, a signature actually left the process, and the locally decoded RPC transaction contains exactly one successful System Program transfer from the signing payer to the configured vault for the exact assessed lamports. The event uses the transaction signature as its idempotency identity: an identical replay is a duplicate, while a different amount, payer or vault under the same signature is rejected. The fill event for this path reports `fee = 0`, so the separately verified fee is not double-counted as a fill fee. Mock-RPC and unit tests cover exact amount, balanced cash/fees postings, replay and conflicting replay; `evidence/platform-fee-review/confirmed-fee-ledger-{before,after,copy-suite,checks}-2026-11-09.txt`.

This is a **tenant fee expense**, not platform revenue, a vault receipt reconciliation, or proof of payout. It covers only copy direct native-SOL fee legs; Jupiter/WSOL fees, Polymarket, sniper, Telegram, address-lookup transactions, inner instructions, other fee surfaces, historical fabricated rows, restart replay, production RLS credentials, real RPC commitment/authenticity and live-chain settlement remain OPEN. Provider metadata, slot and commitment are still trusted. A ledger rejection is surfaced as a post-trade module error but does not reverse the trade. **Phase 1.1 remains OPEN.**

### Telegram command-id payload binding and live sell scope (2026-11-09)
A Telegram command id is no longer a bare replay key. `OrderRequest::payload_fingerprint()` SHA-256 hashes the command identity, tenant, chat/user, action, mint, amount/percent and slippage. Both the in-memory fake port and the deployment port bind a completed receipt to that digest; reusing the same id with different economics returns `PortError::PayloadMismatch` instead of an unrelated receipt. `command_id` must equal `idempotency_key`. On restart, the deployment port reconstructs a receipt only when the deterministic trade's note carries the exact versioned fingerprint; legacy trades without it fail closed. Red tests showed both ports previously replayed the original receipt for a changed payload; green evidence: `evidence/platform-fee-review/telegram-payload-mismatch-{before,module-after,server-after}-2026-11-09.txt`.

Live Telegram SELL no longer uses the wallet-wide token balance as the notional for one tracked position. The wallet raw balance and the tracked position raw quantity must agree within one raw rounding unit; larger differences fail closed with an audited risk rejection, and the sell is capped to the smaller value. This is a conservative one-position parity check, not multi-position/token-account provenance, reconciliation of stale or untracked exposure, or live-chain proof.

These are process-local / repository guards. The in-memory receipt memo is lost on restart unless the durable trade note is present; fingerprint notes are not cryptographically signed, and a compromised state store could forge one. No durable cross-replica command reservation, confirmed-fill fee posting for Telegram, or platform revenue settlement is established. **Phase 1.1 remains OPEN.**

### Checked write-ahead intent reservation — fail-closed record (PARTIAL, 2026-11-09)
`IntentSink::record_checked` is a new opt-in contract. Red core test showed the wrapper previously called the best-effort `record` and let execution proceed; after the fix, core recovery 11/11 and the production `DbIntentSink` PostgreSQL regression 1/1 pass, with affected crates Clippy `-D warnings`, fmt and diff-check PASS (`evidence/platform-fee-review/intent-reservation-gate-{before,after}-2026-11-09.txt`).

The production-RLS success path and multiple OS processes are not proven by these tests. Default sinks and deployments without a checked sink retain their previous best-effort semantics. **Phase 1.1 remains OPEN.**

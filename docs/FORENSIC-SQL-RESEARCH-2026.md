# FORENSIC SQL RESEARCH (2026-10-06)

EVIDENCE-LEVEL: CODE

Forensic sweep of EVERY SQL statement in the product against the
tenant-isolation contract. Generated by `scripts/forensic-sql-scan.sh`
(612 Rust files swept, 500 `sqlx::query` call sites, 478 inline
statements extracted and classified); the companion regression gate is
`tests/forensics/sql-pattern-regression.sh`. Nothing in this document
is hand-counted: every number below is machine-measured by the scan,
and the scan is the same one the release test runs.

## How to reproduce

```bash
scripts/forensic-scan                    # typo-guard: see below
scripts/forensic-sql-scan.sh             # the sweep; exit 0 = zero class-4
tests/forensics/sql-pattern-regression.sh  # regression gate (fails on class-4)
```

(The correct command is `scripts/forensic-sql-scan.sh`; the regression
test is the gate that must stay green.)

## The five forensic classes

| Class | Name | Meaning |
| --- | --- | --- |
| 1 | tenant-safe | `organization_id` is enforced INSIDE the SQL: a WHERE/ON predicate, an INSERT column, or an ON CONFLICT arbiter |
| 2 | intentional-global | deployment-global by design and documented: the audit hash chain, provider-event idempotency, the identity-resolution KV plane, the GlobalRiskOracle gate, the HA plane, migration bookkeeping |
| 3 | operator-only | reachable only from the operator / runtime / retention plane; no tenant can reach the statement through the tenant data plane |
| 4 | missing-tenant-enforcement | tenant data touched with NO org scope in the SQL and no sanctioned global reason. **This is the class that fails the build.** |
| 5 | cosmetic | test fixtures, enforcement tests, non-SQL text — no product surface |

Classification rule for "org-scoped" is strict on purpose: an
`organization_id` that appears only in a SELECT projection (e.g.
`SELECT organization_id, version FROM t` with no WHERE) is **not** an
org predicate and does not count as scoped.

## Defects this sweep found and fixed (2026-10-01)

1. **Order-cancel history was attributed to the deployment organization
   (REAL tenant-attribution bug, class 4 → fixed).**
   `crates/core/src/trading_repository/orders/write.rs` cancel path
   inserted `order_status_history` without `organization_id`; the 0024
   `deployment_organization_id()` DEFAULT silently attributed tenant
   cancellations to the deployment org, so a tenant's own history view
   would miss its own cancellations. Fixed with the same org-subselect
   pattern the adjacent insert already used
   (`SELECT organization_id, id, … FROM orders WHERE organization_id = $1 AND id = $2`),
   so the history row can never be attributed to an org the order does
   not belong to.
2. **Tenant lifecycle durable phase update had org enforcement only in
   Rust (class 12 → fixed).** `crates/server/src/saas/tenant_lifecycle.rs`
   `advance_job` verified `job.organization_id` in process but wrote
   `UPDATE tenant_lifecycle_jobs … WHERE id=$1`. The durable WHERE now
   carries `AND organization_id = $4` (defense-in-depth: the write can
   no longer escape its tenant even if the in-process check were
   bypassed).
3. **Five swallowed durable-write results in tenant_lifecycle.rs
   (the custody failure mode, stamped out).** Suspend/resume org status,
   lifecycle-job insert, and session/API-key revocation updates used
   `let _ =` and could fail silently forever. All five now log
   `tracing::warn!` with org/job identity on failure, matching the
   custody hardening.

## Verification the sweep performs beyond classification

* **ON CONFLICT arbiters (G6):** all 11 tenant-table upsert arbiters
  carry `organization_id` — the 0026–0034 tenant-composite arbiter
  swaps hold in code, not just in migrations.
* **No cross-tenant JOINs without org equality (G5 = 0).**
* **No string-interpolated SQL (G9 = 0):** every statement binds
  parameters; none is assembled with `format!`/`push_str`.
* **Extraction coverage:** 385 of 400 `sqlx::query` sites have inline
  literals; the scan refuses to report a clean sweep if coverage drops
  (tolerance bound 15). The non-literal sites are typed-query helpers
  (`.map()`-built dynamic filters under `TenantQueryScope`, which the
  `require_org_predicate` enforcement test covers).

## Honest limitations

1. The scan classifies statements, not call graphs: "operator-only"
   (class 3) means the statement lives in the operator plane of the
   codebase; the tenant data plane never routes to it. A future
   call-graph pass could tighten this further.
2. The identity-resolution plane (class 2) enforces org equality at
   the service layer, not in SQL — by necessity, because an
   unauthenticated session token cannot carry a trustworthy org id.
3. `risk_events` attribution to the deployment org in the legacy
   operator plane is a real, documented limitation (per-tenant risk
   attribution exists only through the tenant data plane).

## Regression gate

`tests/forensics/sql-pattern-regression.sh` runs this scan and fails
the release on ANY class-4 finding, and additionally proves the scanner
detects a planted unscoped statement (a scanner that cannot fail is
worthless). Both checks must stay green.
